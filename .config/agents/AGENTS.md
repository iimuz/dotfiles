# AGENTS.md

## 言語

ユーザーに向けた出力は、入力の言語に関わらず日本語で書く。
skill やリポジトリの規約が成果物の言語を決めているとき (コミットメッセージなど) は、
その成果物に限ってそちらに従う。

- 実装物でない成果物 (ADR、レポート、計画、設計文書) は日本語で書く
- subagent への prompt は、token を節約するため英語で書く

## 設計の判断

- 将来の拡張性より今の要件を優先する (YAGNI)
- 理論上の正しさより保守のしやすさを優先する
- 凝った解決や技法より、単純で読みやすいコードと標準的なイディオムを選ぶ (KISS)
- 重複は 3 回目が現れるまで許し、3 回目で抽象化を検討する (Rule of Three)
- 実験的なライブラリより、枯れて安定した技術を選ぶ
- 不変性 (immutability) を好み、オブジェクトや配列を書き換えない
- 関連するコードは同じモジュールにまとめる (Locality of Behavior)。
  ファイルを分けるのは、独立して読めて変えられるまとまりができたときにし、行数だけを理由に分けない
- セキュリティの水準をプロジェクトの範囲 (個人、社内、公開) に合わせる

## コードのコメント

コメントに書くのは、コードから読み取れない WHY だけにする。
隠れた制約、回避策の理由、読み手が驚く振る舞いがこれにあたる。
変更履歴、移行の経緯、task や issue の ID は、コメントではなくコミットメッセージか PR の説明に書く。

## 情報の境界

セッションで読んだ内容を、別の場所に残るものへ具体的に書いてよいのは、書き込み先の持ち主が
情報源と同じで、公開範囲が同じか狭いときだけにする。
それ以外は、固有名、パス、番号、URL、設定値、ログの抜粋を残さない一般的な言葉に書き直す。
言い換えや要約も、別のセッションや subagent への依頼文も同じに扱う。
依頼を受けた側がその文を書き込み先に写すことがある。
この規則は、プロジェクトの範囲 (個人、社内、公開) によって緩めない。

- 持ち主は organization やアカウントを単位にする。仕事の organization と個人のアカウントは、公開範囲が
  同じでも持ち主が違う。ローカルのノートと memory は、書いたときの作業の持ち主と公開範囲を引き継ぐ
- 公開されている情報は対象にしない。ただし、範囲の狭い情報源がそれをどこでどう使っているかは対象にする
- 持ち主か公開範囲が分からないものは、公開されていないものとして扱う。
  リポジトリは `gh repo view <owner>/<repo> --json nameWithOwner,visibility` で確かめられる
- ユーザーが持ち出す内容と書き込み先を明示して指示したときは、その範囲に限ってそのまま書いてよい
- 書き直すと意味が通らないときは、書かずにユーザーに確かめる

## 作業の進め方

- ユーザーが明示的に指示しない限り、GitHub の Issue や Pull Request に書き込まない (コメント、ラベル、
  担当者の割り当て)
- 出力が context を埋める作業、対象が未特定の広い探索、独立して並列にできる作業は、頼まれなくても
  subagent に委譲する。それ以外は main agent が直接やる。
  委譲は毎回文脈を作り直すぶん高くつき、要約を経て細部が落ちる
- orca-cli と orchestration は、ユーザーが Orca、worktree、別のエージェントを名指ししたときだけ使う。
  単に handoff や引き継ぎと書かれたときは使わない
