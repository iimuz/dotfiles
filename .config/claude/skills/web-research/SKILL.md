# Web Research

## Overview

2 段階の調査を行う。第 1 段階では参照した記事ごとに、単独で読める要約をファイルとして書く。
第 2 段階ではその要約だけを読んで最終要約を作る。これにより最終要約のどの主張も
記事単位の要約に遡れる。1 回で統合する通常の調査ではこの追跡ができない。

## Output Layout

カレントプロジェクト配下に次の構成で作成する。

```text
docs/reports/YYYY-MM-DD-{topic}/
├── report.md
└── sources/
    ├── 01-{slug}.md
    └── 02-{slug}.md
```

- `YYYY-MM-DD` は今日の日付。`{topic}` は調査主題を kebab-case にしたもの。
- `NN` は 2 桁ゼロ埋めの通し番号。選定順に採番し、`report.md` の引用番号と一致させる。
- `{slug}` は記事タイトルまたはドメイン名を kebab-case にしたもの。

## Process

1. Scope。質問を 3 から 5 個の重複しない調査観点に分解する。検索を始める前に観点をユーザーに示す。
2. Search。観点ごとに WebSearch を実行する。ホスト名とパスを正規化して重複を除き、
   関連度で順位付けして全観点の合計で最大 8 件を選定する。ユーザーが件数を指定した場合はそれに従う。
3. Summarize each article。1 ソースにつき 1 サブエージェントを並列でディスパッチする。
   ディスパッチ時に、対象 URL、割り当てた `NN`、`{slug}`、出力先ディレクトリの絶対パス、
   元の調査質問を渡す。`NN` はオーケストレーターが採番し、サブエージェントには決めさせない。
   各サブエージェントは次を行う。

   - context-mode MCP が利用できる場合は `ctx_fetch_and_index` でページを取得し、続けて
     `ctx_search` で `source` を絞って本文を読む。取得だけではプレビューしか返らない。
     ノートに書く要点を網羅するよう複数のクエリを発行し、必要に応じて `limit` を上げながら、
     要約と引用に足る本文が揃うまで `ctx_search` を繰り返す。
     context-mode が利用できない場合は WebFetch を使う。
   - [references/source-note-template.md](references/source-note-template.md) に従って
     `sources/NN-{slug}.md` を書く。
   - 戻り値はファイルパスのみとする。記事本文を返さない。

4. Synthesize。サブエージェントを 1 つディスパッチし、`sources/` 配下のノートだけを読ませて
   [references/report-template.md](references/report-template.md) に従って `report.md` を書かせる。
   ディスパッチ時に、`sources/` ディレクトリの絶対パス、元の調査質問、ステップ 2 で使用した
   検索クエリ、選定から除外したソースとその理由、取得に失敗したソース、`report.md` の出力先
   パスを渡す。戻り値はファイルパスのみとする。このサブエージェントには Web 取得ツール
   (WebSearch, WebFetch, ctx_fetch_and_index) を使わせない。ノートの記述が薄い場合も、
   ノートに無いことは書かせない。
5. Trace check。読み取り専用の検証サブエージェントを 1 つ立て、`sources/` 配下の全ノートと
   `report.md` を実際に読んで突き合わせさせる。照合対象は `report.md` の TL;DR と Findings の
   2 節に限る。Question、Sources、Research Log はオーケストレーターが付与する進行管理用の
   情報であり、ノートには由来しないため照合対象から除く。確認するのは、`report.md` のすべての
   主張に `[NN]` 引用があること、すべての `[NN]` が実在するノートを指すこと、ノートに無い情報が
   混入していないことである。`[01] [03]` のように複数の
   ノートを併記した文は、併記した各ノートが単独でその文を裏付けているかを個別に確認する。
   片方しか裏付けない場合は、文を分割してノートごとに引用を付け直す必要があると判定する。
   ノート間の比較や記載の不在に関する主張には、比較対象としたノートすべての番号が付いて
   いるかを確認する。この検証サブエージェントは `report.md` を書き換えず、違反の一覧のみを
   オーケストレーターに返す。オーケストレーターはノートだけを根拠に `report.md` を修正し、
   違反が無くなるまで本ステップを繰り返す。ただし繰り返しは最大 3 回までとし、3 回を終えても
   ノートの記述だけでは解消できない違反が残る場合は、`report.md` に無言で残さずユーザーに
   報告する。
6. Adversarial verification。ユーザーが明示的に要求した場合のみ実行する。主要な主張ごとに
   サブエージェントをディスパッチし、反証となる情報を Web 検索させる。この反証調査サブ
   エージェントの戻り値は URL とその真偽判定のみとし、記事本文を返させない。反証が見つかった
   場合は、その出典にも要約サブエージェントを立ててノートを書かせる。`NN` は既存の連番の
   続きをオーケストレーターが割り当てる。`report.md` の該当する主張に `[NN]` 付きで注記する。
   ノートを作らないまま `report.md` に追記しない。注記を追加した後は、ステップ 5 を再実行する。

## Rules

- 統合はノートのみを読む。統合の段階で新しいソースを追加しない。記事本文を最終要約に直接使わない。
- `report.md` のすべての主張に、根拠となったノートの引用を付ける。
- 選定したソースには必ずノートを書く。取得に失敗したソースにもノートを書く。
- 取得できなかった内容を推測で埋めない。取得失敗として記録する。
- 出力は日本語で書く。逐語引用は原語のまま残す。
- 生成する Markdown は lint に適合させる。1 行目を H1 にし、本文行は 120 文字以内にし、
  リストの前後に空行を入れる。URL は `<https://example.com>` のように山括弧で囲む。
  `<file>` のような山括弧を含む CLI 記法はバッククォートで囲む。素のまま書くと URL は MD034、
  山括弧は HTML と解釈されて MD033 で lint に失敗する。
  引用番号を `[01][03]` と続けて書くと参照リンクと解釈されて MD052 で失敗するため、`[01] [03]` と
  空白で区切る。

## Fetch Failures

Cloudflare や有料記事の壁があるページは HTTP 403 を返す。JavaScript による描画が必須のページは
中身の無い HTML を返す。いずれの場合もノートとレポートのソース一覧に「取得失敗」と記録する。代替ソースの探索は、
並列で走らせた要約サブエージェントが出そろった後にオーケストレーターが行う。選定の重複を
避けるため、取得に失敗したサブエージェント自身には探させない。代替ソースにも要約サブ
エージェントを立て、`NN` は既存の連番の続きをオーケストレーターが割り当てる。

WebFetch はページそのものではなく小型モデルによる要約を返すため、`ctx_fetch_and_index` と
`ctx_search` を組み合わせた場合より忠実度が低い。WebFetch を使った場合はノートの取得方法欄にそれを記録する。

WebSearch が候補を返さない場合は、語を変えて 1 回再検索する。それでも得られない場合は、
何を試して見つからなかったかをユーザーに報告して終了する。推測で調査結果を作らない。

## Scope

Web 上の記事を対象とする。ローカルのファイルやリポジトリを精読する場合は deep-read スキルを使う。
主張単位の敵対的検証を重視する場合は組み込みの deep-research スキルを使う。
