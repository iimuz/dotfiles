# PR の確認と報告

組み込みの `code-review` の結果に、Issue との整合、レビュースレッドの状態、CI を足して、Approve の判定、Merge の条件、短い説明を報告する。
報告はターミナルに出すだけで、GitHub、作業ツリー、ブランチ、stash を変えない。
checkout も fetch もしない。
PR の head のファイルは gh の API で head の commit を指定して読む。

引数: `$ARGUMENTS`

## 入力

書式は `<PR番号> [--range <base>...<head>] [--level <low|medium|high|xhigh|max>] [資料 ...]` とする。

- PR 番号が無ければ、この書式を示して止まる
- `--level` の既定は `medium` とする
- `--range` はローカルにすでにある参照で書く。
  `code-review` の対象だけを狭め、説明、整合、スレッド、Merge の条件は PR 全体を対象にする。
  範囲の head を `git rev-parse` した commit が PR の `headRefOid` と違うときは、古い範囲を見たおそれとして報告の「人が見る点」に書く
- 資料はファイルのパス、URL、チケットの ID で、いくつでも並べてよい。
  要件の資料に加える

## 流れ

1. 最初に Skill tool で `code-review` を `args: "<level> <対象>"` として呼ぶ。
   `<対象>` は `--range` があればその範囲、無ければ PR 番号とする。
   level は省かない
2. `code-review` がバックグラウンドで動いて起動したことだけを返したときは、完了の通知を待つ間に次の手順を進める。
   同期で指摘が返ったときは、そのまま次へ進む
3. [references/commands.md](references/commands.md) のコマンドで、PR の状態、差分、CI、Issue、スレッド、レビュー本文、会話欄のコメントを集める。
   PR を gh で読めなければ、gh のエラーを見せて止まる。
   アカウントは切り替えない。
   `code-review` が `git diff` の失敗で終わったら、git のエラーを見せて止まり、報告を推測で埋めない
4. `code-review` の指摘がそろうまで報告を書かない。
   そろったら、指摘ごとに示されたコードを PR の head で読んで確かめる (「`code-review` の指摘の扱い」)。
   `code-review` は周りのコードを作業ツリーから読むので、作業ツリーが head と違うと行や文脈がずれることがある
5. [references/report.md](references/report.md) の形で報告を出す

## 意図の取り方

エージェントが作った PR の本文は、作者の自己申告であり、何を頼まれたかの根拠にならない。
意図は PR の外の資料から取る。

- 要件を定めるのは、closing キーワードで紐づいた Issue である。
  本文で `#N` と参照しただけの Issue は、本文もコメントも背景として読み、要件には数えない
- PR の作者が折りたたみのコメントとして付けた設計や計画は、要件に数えない。
  説明を書く手がかりとして読み、Issue と食い違う点は整合の節に `[計画と Issue の食い違い]` として並べ、判定は Issue に照らして出す。
  人が承認した設計を要件にしたいときは、引数で渡された資料を使う
- PR の本文が Issue の範囲を明示しているときは、その範囲を受け入れる。
  範囲から外した要件は blocking にせず、`[範囲外]` として並べる
- Issue の本文とコメントにあるリンクのうち、GitHub の Issue と PR、同じリポジトリのファイルは 1 段だけたどって読む。
  外部のサービスのリンクはたどらず、`[読んでいない資料]` として挙げる
- 要件の資料を自分で探しに行かない。
  読むのは、PR と Issue、そこから 1 段のリンク、引数の資料だけである
- Issue も引数の資料も無い PR は、PR の本文を仮の意図として使い、そのことを整合の節に書く。
  何も見つからないときは推測で埋めず、「確かめる資料が無い」と書いて、判定を `人の判断が要る` にする

## 判定

Approve の判定と Merge の条件は別々に出す。
draft を判定に混ぜない。

Approve の判定は次の 3 つのどれかにする。
2 つ以上に当たるときは `対応が要る` を優先し、判断が要る点も並べて書く。

- `Approve してよい`: blocking の指摘が無く、解決していないスレッドは Nit や任意と明示されたものか、bot や自動のレビュアーのものだけである
- `対応が要る`: blocking の指摘があるか、作者の対応を待つスレッドがある。
  誰が何をするかを一覧にする
- `人の判断が要る`: blocking の指摘は無いが、skill では決められない点がある。
  次のものがこれにあたる
  - 要件の資料が見つからない
  - 要件に無い変更を受け入れるか
  - Issue や設計で決まったことへの異論
  - 「判断が要る」と「レビュアーの確認待ち」のスレッド

スレッドの分類との対応:

- `[作者の対応待ち]`: `対応が要る`
- `[判断が要る]`: `人の判断が要る`
- `[レビュアーの確認待ち]`: `人の判断が要る`。
  変更か返信を読み、指摘に応えているように見えるかを 1 行で添える。
  resolve するかはレビュアーが決める。
  対応が要るものの一覧には `[レビュアー]` として載せる
- Nit や任意と明示されたスレッドと、bot のスレッドは判定を変えない。
  ただし、コードを読んで欠陥を確かめたものは `対応が要る` にする

blocking にするのは次の 3 種類だけにする。

- 要件の資料が求めることを、PR が満たしていない
- 要件の資料に合否の基準があり、PR がそれに合わない
- 正しさの欠陥で、失敗する入力と誤った結果を具体的に示せて、コードを読んで確かめたもの。
  `code-review` の指摘もこれに含める

次は blocking にしない: Nit、この PR より前からある問題、確かめきれなかった懸念、要件に無い変更、Issue や設計で決まったことへの異論。

Merge の条件は、CI の最新の結果、コンフリクトの有無、draft かどうか、必須の承認を満たしたかを示す。
表記は report.md に従う。

## `code-review` の指摘の扱い

指摘ごとに、示されたコードを読んで失敗の筋書きを確かめ、英語の指摘を日本語の 1 行に書き直す。

- 確かめた欠陥は blocking にする
- 誤りと分かった指摘は報告に入れず、件数だけを書く
- 確かめきれなかった指摘は `[懸念]` として blocking でない指摘に並べる

## スレッドの状態

- 解決済みのスレッドは件数だけを書く。
  解決していないものは、次に誰が動くかで 3 つに分ける
  - `[レビュアーの確認待ち]`: 指摘に応える変更か返信があるが、resolve されていない
  - `[作者の対応待ち]`: 指摘に応える変更も返信も無い
  - `[判断が要る]`: 設計の判断や方針を問うていて、コードの変更では片づかない
- 対象は、レビュースレッド、COMMENTED と CHANGES_REQUESTED のレビュー本文、PR の会話欄のコメントである。
  会話欄のコメントには resolve の状態が無いので、後の返信と commit から判定する。
  レビュー本文は、同じレビュアーが後で APPROVED のレビューを出していれば解決済みに数える
- PR の作者自身のコメントは、レビュアーの指摘として数えない
- bot のスレッドは作者の対応待ちに数えず、blocking でない指摘と同じ扱いで `[bot]` として並べる
- レビュアーが Nit や任意と明示したスレッドは、未対応でも作者の対応待ちに数えず、`[Nit]` として並べる
