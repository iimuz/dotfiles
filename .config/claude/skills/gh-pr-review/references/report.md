# 報告の形

報告はターミナルに出すだけで、ファイルに書かない。
節は次の順に並べる。

1. 判定と Merge の条件
2. 対応が要るもの
3. 説明
4. 意図との整合
5. スレッドの状態
6. blocking でない指摘

## ラベル

- 判定: `Approve してよい`、`対応が要る`、`人の判断が要る`
- Merge の条件の 1 行: `CI <結果> / コンフリクト <有り|無し|未確定> / <draft|ready> / 必須の承認 <済み|未|無し>`
  - CI の結果は `成功`、`失敗 N 件`、`実行中`、`無し` のどれか
  - `mergeable` が `UNKNOWN` のときは `未確定`、`reviewDecision` が空のときは `無し` と書く (`未` と書かない)
  - PR の state が `OPEN` でないときは、`MERGED` か `CLOSED` を行の先頭に書く
- 動く人: `[作者]`、`[レビュアー]`
- スレッド: `[作者の対応待ち]`、`[判断が要る]`、`[レビュアーの確認待ち]`
- 整合: `[未達]`、`[要件に無い変更]`、`[範囲外]` (この PR の範囲外とした要件)、`[読んでいない資料]`、`[計画と Issue の食い違い]`
  - 節の見出しに資料の名前を書く (例: `資料: Issue #N`)
- blocking でない指摘: `[Nit]`、`[懸念]`、`[bot]`
  - 見出しに、誤りと確かめて除いた指摘の件数を書く

## 説明の 3 節

どれも数行に収める。図は Mermaid にせず、箇条書きか簡単な文字の図にする。

- 全体の構成: 変更が載るシステムの部品と、そのつながりを示し、この PR がどこに触れるかを書く
- 何が変わったか: 変更を意味のまとまりに分け、まとまりごとに 1 行で書く。挙動が変わる点は「前は X、今は Y」の形で書く
- どう確認するか: 次の 4 点を書く
  - 読む順番: 主要な変更から読み、ファイルごとに見どころを 1 行添える
  - 動かして確かめる手順
  - テストが守る範囲と守らない範囲
  - 確かめきれず人が見るべき点

## 件数の書き方

満たしている要件と解決済みのスレッドは件数だけを書き、一覧には問題のあるものだけを並べる。
指摘は件数を絞らず、1 件を 1 行に縮める。

## 骨組みの例

```text
判定: 対応が要る
Merge の条件: CI 失敗 1 件 / コンフリクト 無し / draft / 必須の承認 未

対応が要るもの
- [作者] 要件「...」が未実装 (path/to/file)
- [作者] スレッド「...」に未対応 (path:line)

説明
- 全体の構成: ...
- 何が変わったか:
  - ...
- どう確認するか:
  - 読む順番: path/a (...)、path/b (...)
  - 動かして確かめる: ...
  - テストの範囲: ...
  - 人が見る点: ...

意図との整合 (資料: Issue #N)
- 満たしている要件: 4 件
- [未達] ...
- [要件に無い変更] ...

スレッドの状態 (解決済み 3 件)
- [作者の対応待ち] path:line ...
- [判断が要る] ...

blocking でない指摘 (誤りと確かめて除いた指摘 1 件)
- [Nit] path:line ...
- [懸念] path:line ...
```
