# 文書の書き方

## 書式

- 節は `##` 以下の見出しで分ける
- 箇条書きはハイフン (`-`) で書く
- 太字、斜体、水平線は使わない
- 図は Mermaid のコードブロックで書き、図種は図描画の skill に従う

## 言語

- 文書、skill、rules は日本語で書く
- 識別子、コマンド、ファイル名、lint ルール ID は原文のまま書く

## リンク

- リポジトリ内ファイルへのリンクは、リンク元ファイルからの相対パスで書く。
  先頭スラッシュは使わない
- 行番号を書かない。編集で腐る。関数名、定数名、lint ルール ID で位置を示す
- リンク行には、リンク先に何があるかではなく、どういうときに読むかを書く。
  素のリンクは起動時に展開されず、読むかどうかはモデルが決める
  - 効きにくい: `- [Frontmatter](docs/design/frontmatter.md)`
  - 効く: `- frontmatter にフィールドを足すときは [Frontmatter](docs/design/frontmatter.md) を読む`

## 置かないもの

新しい世代のモデルで逆効果になる記述を置かない。

- CRITICAL、MUST、全大文字による強調。過剰発火の原因になる。「... のときに使う」と平叙で書く
- 自己検証、二重確認、再確認の指示。既定で自己検証するため過剰になる
- 同じ指示の防御的な反復。1 か所に書く
- 「保守的に」「重大なものだけ報告する」のような出力を絞る指示。字義どおりに従われ、報告漏れになる
- ファイルを読めば分かること。ディレクトリ構成、依存パッケージの一覧、技術スタックの列挙
- 変更履歴、移行の経緯、issue 番号への参照。置き場所は [placement.md](placement.md) にある
- 埋め草の節、重複する要約、定型の前置き

順序や網羅性に意味がある番号付きの手順は残す。検証の方法と基準も残す。lint や script の実行手順、
独立した検証者に渡す rubric がこれにあたる。
